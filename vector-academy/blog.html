FIELD NOTES

Ideas for building AI that works.

Practical notes on choosing a problem, evaluating a system, and taking a prototype into the world.

BUILDING5 MIN READ

Start with the problem, not the model.

It is tempting to begin with the newest model or framework. A better first step is to describe the task in plain language: who needs help, what information is available, and what a useful result looks like.

That brief gives you a way to make engineering choices. It can reveal whether a simple retrieval workflow is enough, where a person should review the result, and how you will know whether the system helped. Choose the model and tools after those needs are clear.

EVALUATION4 MIN READ

A convincing demo is not an evaluation.

A demo shows that a system can work once. An evaluation helps you understand how it behaves across the cases that matter. Write down representative inputs, expected outcomes, and the kinds of mistakes that would be costly.

Run the same cases after each meaningful change and record what improved or regressed. Even a small, carefully chosen set of examples gives a team a more reliable basis for decisions than a handful of impressive outputs.

ENGINEERING6 MIN READ

Design the fallback before you need it.

AI components can be uncertain, slow, or unavailable. Decide early what the product should do when an answer is incomplete, a tool call fails, or a request takes too long. A clear fallback is part of the user experience, not an afterthought.

Keep important steps observable, make uncertainty visible where it matters, and provide a safe route to retry or ask for help. These small design choices make the system easier to trust and easier to maintain.
